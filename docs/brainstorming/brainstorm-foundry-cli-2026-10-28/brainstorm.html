Technique I
SCAMPER Method
Systematic mutation of the core concept -- substitute, combine, adapt, modify, put to other use, eliminate, reverse.
Substitute
Coach
Substitute Claude Code SDK for provider-agnostic agent slot interface -- builder agent becomes pluggable (Cursor, Aider, Codex CLI, Ollama).
User
Substitute CLI prompt checkpoints for local web UI -- Foundry spins up a server, opens browser for reviewing/editing docs with rich text, terminal stays for progress streaming.
Combine
Coach
Combine checkpoint UI with live project dashboard -- browser tab stays open whole run, shows doc editor during planning, CI-style view during build, approve button lives next to context.
User
Combine forge.log with git history -- every Foundry decision is a structured commit message, git log IS the forge.log, repo tells full story of how it was built.
Adapt
Coach
Adapt IaC pattern: foundry.yaml as declarative process spec -- describes the pipeline not just the output, forkable/reproducible project genesis.
User
Adapt database migration pattern: foundry.lock records exact prompt versions, model versions, agent versions, response hashes -- replayable, diffable, re-runnable per phase.
Modify
Coach
Modify linear pipeline into DAG with backtracking -- foundry rewind --to prd preserves history, re-derives downstream, git captures both paths.
User
Modify retry loop to escalate-to-human: auto-retry once, then pause with full context in checkpoint UI, human can edit story/code/skip, intervention logged in foundry.lock as hint for future runs.
Put to Other Use
Coach
Teaching tool -- students run Foundry on an assignment, then critique every AI decision using the git log and foundry.lock as case study material.
User
Technical interview tool -- candidate runs Foundry with all checkpoints manual, interviewers evaluate engineering judgment not coding speed, foundry.lock becomes review artifact.
Eliminate
Coach
Eliminate GitHub repo creation from pipeline -- build locally, export as tarball/repo/zip/docker at the end, repo is distribution format not build artifact, works offline.
User
Eliminate deployment target as Foundry concern -- output Dockerfile + health check + ports declaration as universal interface, where it runs is not Foundry's problem.
Reverse
Coach
Reverse direction: foundry reverse inspects running app or codebase and generates brainstorm/PRD/architecture/epics that would have produced it -- reverse-engineers intent from implementation.
User
Reverse approval flow: human authors PRD/arch first, Foundry adapts to it -- foundry build --from-prd, AI fills gaps and flags ambiguities instead of proposing, slots into existing team workflows.
Anvil Strike
Technique II
Chaos Engineering
Injecting failure into the forge. What breaks when the fire goes out mid-pour?
Failure: Hallucinated Dependency
Coach
LLM hallucinates nonexistent dependency, mocks hide it, Dockerfile fails -- need verify-deps step between architecture approval and implementation.
Failure: Inconsistent PRD
User
Human approves internally inconsistent PRD, Foundry builds it faithfully but wrong -- need contradiction detector as hard stop before architecture, resolution logged as first-class decision.
Failure: Model Drift
Coach
Model version changes mid-run after crash/resume, codebase has style uncanny valley -- need model pinning in foundry.lock or post-build consistency pass.
User
Pin model version + human override at resume: continue with same model or switch and add mandatory consistency pass as final epic, model identity is first-class build parameter like compiler version.
Model identity is a first-class build parameter -- Foundry should never silently switch models mid-run.
Failure: Information Loss Between Stages
Coach
Brainstorm has 13 dirs, PRD silently covers 9 -- need traceability matrix with explicit mapping between stages, human decides what to drop.
Failure: Infrastructure Conflation
User
GitHub rate limit mid-run, retry loop treats infra failure as code failure, LLM corrupts working code -- need 3 failure categories: code (LLM fixes), infra (pause+wait), environment (hard stop).
External failure is the normal case not the edge case -- Foundry talks to 4+ services and must treat partial outages as routine.
Quench
Technique III
Kill the Crown Jewel
What if BMad planning -- the centerpiece -- was ripped out? What survives?
User
Kill BMad planning reveals product split: Foundry Pro (full pipeline) vs Foundry Quick (skip to code, vibe coding with guardrails) -- shared engine, lock file, CI/CD.
The Real Crown Jewel
The crown jewel is foundry.lock + structured git history, not BMad. Provenance and traceability are what make it Foundry. BMad is the most powerful mode, not the only one.
User
Minimum viable Foundry Quick: (1) self-written spec as first checkpoint, (2) incremental logical commits not file dump, (3) tests non-negotiable before commit -- these three separate it from raw LLM.
Core Foundry value proposition: structure (explicit contract), incrementality (navigable history), verification (tests required) -- not the planning brain, not the deployment.
Build strategy: Foundry Quick is the MVP shipped first -- proves core value without BMad dependency, Foundry Pro adds planning on top.
Temper
Technique IV
Utopia vs Dystopia
Two futures. Same tool. Different intent.
Utopia

4000+ foundry.yaml templates. SaaS starter deploys in 22 minutes. foundry reverse for onboarding. Lock files as provenance standard. Stanford CS course uses Foundry.

Dystopia

Founder rubber-stamps 14 checkpoints in 8 minutes. JWT bug ships. Lock file becomes liability evidence not provenance. Foundry created false sense of due diligence.

User
Anti-rubber-stamp design: minimum read time, required acknowledgment of specific decisions, explicit "approving without reading" flag in lock file, protect human from false confidence.
The audit trail is a weapon that cuts both ways -- it proves diligence or proves negligence. Foundry must make rubber-stamping harder, not easier.

Final Pour
Convergence
MoSCoW Prioritization
The molten ideas, cast into ranked steel.
Must Have
  • Foundry Pro -- full BMad pipeline orchestration
  • foundry.lock -- provenance, versioning, reproducibility
  • Git-as-forge-log -- structured commit messages as audit trail
  • 3-category failure taxonomy -- code / infra / environment
  • Dockerfile output as universal deployment interface
Should Have
  • Foundry Quick mode -- skip planning, keep guardrails
  • Checkpoint web UI -- rich editing in browser
  • Pre-flight analysis -- contradiction detection on ingest
  • Escalate-to-human on failure -- pause, don't loop
Could Have
  • foundry.yaml declarative process spec
  • Dependency verification step
  • Anti-rubber-stamp checkpoint design
  • --from-prd human-authored spec ingest
Won't Have (this round)
  • foundry reverse (reverse-engineer intent from code)
  • DAG backtracking pipeline
  • Live dashboard
  • Template registry
  • Teaching / interview modes
Key override: BMad is MUST not COULD -- without it Foundry is a better shell script. The lock file needs 50+ decisions to justify itself. The planning pipeline is the product.
The Alloy
Synthesis
Foundry is an observable AI process -- inspectable, replayable, auditable development. Not just a code generator.
LINK
--from-prd and contradiction detector are one feature. Pre-flight analysis is the ingest layer all specs pass through -- whether AI-generated or human-authored.
LINK
Failure taxonomy and anti-rubber-stamp share a principle. Make human/AI responsibility boundaries explicit and honest. Never blur who decided what.
